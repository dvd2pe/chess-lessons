# 5. DEEP WEBSITE MIRRORING & GAME RECONSTRUCTION ENGINE

This is a core subsystem and must be implemented as a dedicated acquisition and reconstruction pipeline.

A simple HTML download is not sufficient.

The objective is to create a local reconstruction of the original game and all discoverable resources and dependencies necessary to run it.

The system must distinguish three different outcomes:

**WEBSITE MIRROR:** A local copy of the original page and its acquired resources.

**GAME MIRROR:** A reconstructed local version of the actual game and its required resources.

**STANDALONE GAME:** A game that operates independently of the original hosting infrastructure to the extent that its functionality has been successfully reconstructed.

The ultimate objective is a verified standalone game, not merely a downloaded webpage.

- Loading screens.
- Game entry points.

# 32. DEVELOPMENT RULES

These rules are mandatory.

1. Build a real functioning application, not a visual mockup.
2. Preserve the original game and all original assets.
3. Deep mirroring and original-game verification come before reskinning.
4. Reskinning and cleanup are optional subsequent operations.
5. A website mirror is not automatically a playable game mirror.
6. A playable game mirror is not automatically an offline standalone game.
7. A successful compilation is not proof of gameplay functionality.
8. Never silently overwrite files.
9. Never automatically modify approved assets.
10. Never delete uncertain dependencies.
11. Preserve technical compatibility.
12. Record every modification.
13. Support rollback.
14. Make uncertainty visible.
15. Distinguish analysis, inference and verified facts.
16. Do not invent successful tests.
17. Do not claim support for an engine or format without implementation evidence.
18. Prefer functional incremental delivery over nonfunctional complexity.
19. Implement proper error handling and recoverable jobs.
20. Do not expose secrets or credentials in the frontend.
21. Keep all original project files recoverable.
22. Make destructive operations explicitly reviewable.
23. Prioritize data integrity and game functionality over cosmetic convenience.
24. Maintain separate acquisition, reconstruction, working, approved and exported versions.

## FINAL PHILOSOPHY

The AI must understand the website before acquiring the game.

It must understand the game's architecture before reconstructing it.

It must understand dependencies before attempting to remove them.

It must understand the game before modifying its assets.

It must understand the reference before generating replacements.

It must show its work, explain its decisions and expose uncertainty.

The user must remain in control of visual approval, technical decisions and destructive operations.

**The objective is not simply to download a game or replace its graphics. The objective is to turn an existing game project into a fully inspectable, locally reconstructed, independently testable and optionally transformable game through one unified AI-powered platform.**

Build the platform around this philosophy.
